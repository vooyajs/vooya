# 0.2.0-alpha.0 publication and recovery

## Status

The eight candidate packages were published. The complete `verify:release` gate
passed, but the original workflow failed during registry-propagation verification.
Manual recovery, the independent receipt and announcement reconciliation are
**still under verification**. This record does not turn the failed workflow into
a successful run. Official-site deployment is a separate pending step.

## Failure and preserved baseline

The publication log records successful publication of all eight candidates after
the full gate. The subsequent exact-registry check exceeded its propagation
window, so the workflow ended in failure. A metadata timeout is not evidence that
the packages were never published; do not issue new versions or republish them
to work around that outcome.

The original pre-publication `latest-before.json` has been preserved unchanged.
Its SHA-256 is
`a6851aa452f45e7485c691d624d71eaa3e77301ec5ac3d9002763cb12648bf4e`.
It is the authority for existing `latest`, beta and unchanged-package tags;
recovery must not recapture or rewrite it after publication. The independent
recovery receipt must identify the same source commit and candidate set.

The two previously absent packages, preset and provider-rust, acquired `latest`
alongside `alpha` on their first publication. Attempts through npm CLI to remove
`latest` returned HTTP 400. A similar observation appears in
[npm/cli issue #8490](https://github.com/npm/cli/issues/8490); this is not a
permanent npm platform guarantee.

This first-publication deviation is recorded separately from the immutable
baseline. It does not authorize changing existing package tags or broadly
allowing later prereleases to advance `latest`. The future pre-publication
baseline rule is documented in [release operations](../releases.md#first-publication-and-the-latest-baseline).

## Executed registry consumers

Local clean Vue and React applications installed the exact expected registry
versions and verified archive provenance, integrity and dependency pins. Both
passed doctor, strict generated declarations, Rust Component/Store builds,
Chromium interaction and unmount/remount. The transitive provider was resolved
through the published dependency graph, not a workspace alias.

A separate local macOS arm64 consumer installed preset and its complete Vooya
graph from the public registry, with a fresh npm cache and no packed/workspace
runtime fallback. It passed concurrent preparation, managed doctor, ordinary
`npm run dev`, Component/Store browser interaction, Rust editing, deliberate
compiler error and recovery, and `npm run build`. Ambient cargo, rustc, rustup
and wasm-bindgen commands were blocked; the host SDK/linker remained available.

The managed Rust cache already existed and was reused. This run is not a fresh
Rust download, interrupted-install test, clean-machine certification or a new
Windows/Linux registry claim. Fresh-cache platform evidence belongs to the
separate named candidate CI jobs. The ordinary Vue/React registry consumer does
not cover optional preset behavior; that is why the separate consumer was run.
Webpack/Rspack and Solid/Svelte retain their named source-fixture boundaries;
metadata checks alone do not establish registry browser coverage for them.

## Recovery completion checklist

The recovery owner is reconciling exact candidate metadata, existing protected
tags and the explicit two-package first-publication deviation. Before marking
recovery complete, record the independent receipt location and digest, confirm
all candidate GitHub Releases and their package-version tags point to the
release source, and preserve the original baseline and consumer evidence.
Do not mark these pending checks complete merely because npm installation works.

The frozen published tarballs contain the README text present at the release
commit. Subsequent repository documentation corrections do not rewrite those
tarballs; no extra package publication is implied by a README edit.
